1. Conceptos clave

📋
Entidad base
Autorizante
Autorización de pago base.
Tiene un MontoAutorizado (techo máximo) y un MesBase de referencia.
🧾
Pago real
Certificado
Pago efectivo vinculado a un autorizante.
Tiene MontoTotal y MesAprobacion. Se pueden emitir varios a lo largo del tiempo.
📈
Ajuste de precios
Redeterminación
Ajuste por variación de costos.
Tiene Porcentaje, Salto (mes de inicio) y Nro (orden secuencial). Su monto se calcula, no se ingresa manualmente.
🔄
Pago derivado
Reliquidación
Pago generado automáticamente para cada certificado aprobado en un mes posterior al del Salto de una redeterminación (los anticipos financieros no generan reliquidación). El primer certificado post-Salto absorbe retroactivamente el porcentaje ya ejecutado pre-Salto (ver Sección 4, Paso 3b). Representa la parte proporcional del ajuste.

💡 Regla clave del Salto (la comparación es siempre mes a mes, nunca por día): Los certificados aprobados hasta el mes del Salto inclusive determinan cuánto ya se pagó (reducen el faltante); el anticipo financiero también cuenta, porque ya está pagado y no se redetermina. 3. Fórmula del MontoRedet (CalcularMontoRedeterminaciones)

Las redeterminaciones se procesan en orden por Nro (1, 2, 3…), por separado para cada autorizante. Solo se consideran certificados aprobados hasta el mes del Salto inclusive para determinar el porcentaje ya utilizado. Una redeterminación Rechazada o Fuera de Plazo tiene monto cero y no entra en la acumulación (regla R6, Sección 6).
Paso A — Porcentaje de ejecución

Sumamos los certificados del autorizante cuyo mes de MesAprobacion es menor o igual al mes del Salto de la redeterminación. Se incluyen todos los tipos de pago, también el anticipo financiero.

SumaCerts = Σ cert.MontoTotal donde mes(cert.MesAprobacion) <= mes(redet.Salto) // mes(x) = primer día del mes de x. En SQL: EOMONTH(x) PorcentajeUtilizado = (SumaCerts / auth.MontoAutorizado) × 100 // Si MontoAutorizado = 0 → PorcentajeUtilizado = 0
📌 El anticipo financiero (TipoPago = 1) sí cuenta como ejecutado: ya fue pagado y no está sujeto a redeterminación.
Paso B — Faltante

El faltante representa qué porcentaje del autorizante aún no fue pagado al momento del Salto.

Faltante = Max(0, 100 - PorcentajeUtilizado) // Nunca negativo: si ya se pagó el 110%, el faltante es 0
Paso C — MontoRedet para Nro = 1 (primera redeterminación)
MontoRedet[Nro=1] = ( auth.MontoAutorizado × redet.Porcentaje / 100 ) × ( Faltante / 100 )
📌 redet.Porcentaje -> Porcentaje de ponderacion
Paso C — MontoRedet para Nro > 1 (redeterminaciones posteriores)

Las redeterminaciones anteriores del mismo autorizante se suman al monto base, acumulando el ajuste sobre la base ampliada.

MontoRedet[Nro>1] = ( (auth.MontoAutorizado + SumaRedetsAnteriores) × redet.Porcentaje / 100 ) × ( Faltante / 100 )
📌 Ejemplo con R2: MontoAutorizado=$1.000.000, R1.MontoRedet=$50.000, Porcentaje R2=8%, Faltante=30%
→ Base = 1.000.000 + 50.000 = $1.050.000
→ MontoRedet R2 = (1.050.000 × 8/100) × (30/100) = 84.000 × 0,3 = $25.200

4.2 Fórmulas paso a paso

Paso 1 — Porcentaje del certificado respecto al autorizante

Indica qué fracción del MontoAutorizado total representa ese certificado.

cert.Porcentaje = (cert.MontoTotal / auth.MontoAutorizado) × 100 // Ej: $250.000 / $1.000.000 × 100 = 25%
Paso 2 — Condición para generar la reliquidación

Se evalúa para cada combinación de redeterminación y certificado del mismo autorizante.

SI cert.CodigoAutorizante == redet.CodigoAutorizante Y mes(cert.MesAprobacion) > mes(redet.Salto) Y cert.TipoPago ≠ 1 (anticipo financiero) // Solo certificados de meses POSTERIORES al Salto reciben reliquidación // El anticipo financiero no se redetermina, por lo tanto nunca reliquida // El PRIMERO de ellos (ordenados por MesAprobacion y luego Id) absorbe el porcentaje acumulado pre-Salto (ver Paso 3b)
Paso 3a — Cálculo del monto (certificados posteriores al Salto)

Para todos los certificados (excepto anticipos) con mes(MesAprobacion) > mes(redet.Salto), salvo el primero de ellos (ver Paso 3b).

MontoReliq = redet.MontoRedet × ( cert.Porcentaje / 100 )
// Expandido (sustituyendo cert.Porcentaje): MontoReliq = redet.MontoRedet × ( cert.MontoTotal / auth.MontoAutorizado )
// Expandido total para Nro=1 (sustituyendo MontoRedet): MontoReliq = cert.MontoTotal × (redet.Porcentaje/100) × (Faltante/100)
📌 Ejemplo: MontoRedet=$50.000 · cert.MontoTotal=$250.000 · MontoAutorizado=$1.000.000
→ cert.Porcentaje = 250.000/1.000.000 = 25%
→ MontoReliq = $50.000 × 25% = $12.500

Expandido total: $250.000 × 10% × 50% = $250.000 × 0,05 = $12.500 ✓
Paso 3b — Cálculo del monto (primer certificado post-Salto)

Para el primer certificado (ordenando por MesAprobacion y luego por Id) cuyo mes(MesAprobacion) > mes(redet.Salto), el porcentaje acumulado pre-Salto se suma al porcentaje propio: este primer pago absorbe retroactivamente el trabajo ya ejecutado hasta el mes del Salto. Así, cuando los certificados posteriores cubren el faltante, la suma de las reliquidaciones iguala al MontoRedet.

// Variables previas porcentajeAcumulado = (SumaCerts_preSalto / auth.MontoAutorizado) × 100 certPorcentaje = (cert.MontoTotal / auth.MontoAutorizado) × 100
// Fórmula para el primer cert post-Salto MontoReliq = redet.MontoRedet × ( (certPorcentaje + porcentajeAcumulado) / 100 )
📌 Ejemplo: Salto = Jun-2024, primer cert post-Salto = Cert 3 (Ago-2024) por $250.000.
→ certPorcentaje = 250.000 / 1.000.000 = 25%
→ porcentajeAcumulado (Cert1 + Cert2 pre-Salto) = 500.000 / 1.000.000 = 50%
→ MontoReliq = $50.000 × (25% + 50%) = $50.000 × 75% = $37.500

Con la fórmula estándar (Paso 3a) habría dado: $50.000 × 25% = $12.500
✅ Regla de consistencia: El total de todas las reliquidaciones de una redeterminación es igual a MontoRedet × ( cert.Porcentaje post-Salto / 100). Si los certificados futuros cubren exactamente el porcentaje faltante, el total reliquidado iguala al MontoRedet.

6. Reglas de negocio vigentes (decisiones del 22 y 23/09/2026)

Hasta septiembre de 2026 convivían en el código tres variantes de la fórmula (la del camino Entity Framework que usan las pantallas y dos versiones ADO heredadas en CalculoRedeterminacionNegocio.cs), que diferían en los puntos de abajo. Se fijó una única regla, que aplican tanto la aplicación como las vistas SQL del tablero Power BI.
#Regla vigenteQué hacía antes la aplicaciónDónde se aplica
R1 El certificado del mes del Salto cuenta como anterior (ejecutado). La comparación es mes a mes: mes(MesAprobacion) <= mes(Salto). Reliquidan solo los meses posteriores. Comparaba fecha contra fecha con "menor estricto" para lo ejecutado y "mayor estricto" para reliquidar. Un certificado del mismo mes del Salto quedaba en un hueco: no reducía el faltante ni reliquidaba. Paso A · Paso 2 · vistas
R2 El anticipo financiero (TipoPago = 1) sí cuenta como ejecutado, porque ya está pagado y no se redetermina. Por lo mismo, un anticipo posterior al Salto no genera reliquidación. Lo contaba como ejecutado (igual que ahora), pero si caía después del Salto sí le generaba una reliquidación. Una de las versiones ADO heredadas lo excluía de lo ejecutado. Paso A · Paso 2 · vistas
R3 El Paso 3b aplica: el primer certificado posterior al Salto absorbe el porcentaje acumulado pre-Salto. Solo existía en las versiones ADO heredadas; el camino Entity Framework que usan las pantallas no lo aplicaba, aunque esta documentación ya lo describía. Paso 3b · vistas
R4 Los legítimos abonos no participan del reparto del SIGAF por expediente (no deberían compartir expediente con certificados). Queda anotado como posible mejora futura. El camino Entity Framework ya los excluía; las versiones ADO heredadas los sumaban al pool del expediente. Sección 7 (vista de pagos)
R5 Cada autorizante se calcula con sus propios certificados. Bug corregido el 22/09/2026: CalcularMontoRedeterminaciones reasignaba la lista de certificados dentro del bucle, de modo que solo el primer autorizante procesado se calculaba bien y el resto salía con faltante 100 % (monto inflado). Aplicación · vistas
R6 Una redeterminación Rechazada (etapa 35) o Fuera de Plazo (etapa 36) tiene monto cero: no acumula en la base de las siguientes y no genera reliquidaciones. Sigue apareciendo en las grillas con estado DESESTIMADO. Las que están en trámite se calculan normalmente. Definido el 01/10/2026. Se calculaba completa, acumulaba y reliquidaba. En producción eran seis rechazadas (unos 390 millones y 64 reliquidaciones), cinco de ellas provisorias ya reemplazadas por su definitiva, es decir, contadas dos veces. Paso C · Paso 2 · vistas
⚠️ Caso límite a tener en cuenta: un anticipo aprobado después del Salto de una redeterminación no reliquida en esa redeterminación pero sí cuenta como ejecutado para las redeterminaciones cuyo Salto sea igual o posterior a su mes. En ese caso la suma de reliquidaciones queda por debajo del MontoRedet en la parte proporcional del anticipo.

7. Vistas SQL para Power BI

El monto de la redeterminación no está guardado en la base (MontoRedet es una propiedad [NotMapped] que la aplicación recalcula en cada request) y las reliquidaciones son filas virtuales que no existen en ninguna tabla. Para que el tablero Power BI las vea, el cálculo se replicó en vistas SQL dentro de la misma base IVC, en el script Database/vw_PowerBI_Redeterminaciones.sql del repositorio. Se descartó exportar desde la aplicación (dependería de que alguien abra la pantalla) y recalcular con DAX (la acumulación de redeterminaciones anteriores y el prorrateo del SIGAF no se expresan bien sin recursión).

7.2 Cómo funciona cada vista

vw_PBI_Redeterminaciones — el cálculo del MontoRedet

Une Redeterminaciones con Autorizantes por CODIGO_AUTORIZANTE. Para cada redeterminación suma los certificados con EOMONTH(MES_APROBACION) <= EOMONTH(Salto) (R1, R2), calcula PorcentajeUtilizado y Faltante, y resuelve la acumulación de redeterminaciones anteriores del mismo autorizante (Paso C, Nro > 1) con un CTE recursivo ordenado por Nro. Las redeterminaciones sin Salto o sin porcentaje se listan con MontoRedet NULL, igual que en la aplicación. Los porcentajes intermedios se guardan con 12 decimales para que el resultado coincida al centavo con la aplicación.

vw_PBI_Reliquidaciones — Pasos 1, 2, 3a y 3b

Cruza cada redeterminación calculada con los certificados del mismo autorizante de meses posteriores al Salto, excluyendo anticipos (R2). ROW_NUMBER() por redeterminación identifica al primer certificado post-Salto, que recibe el porcentaje acumulado pre-Salto (R3). El expediente sale de EXPEDIENTES_RELIQ por (código de redeterminación, año, mes). La clave estable de cada fila es ReliquidacionKey = RedeterminacionId-CertificadoId.

vw_PBI_Pagos — SIGAF, estado y SADE

Apila certificados reales y reliquidaciones (tipo de pago 3). El devengado de DEVENGADOS se reparte entre todos los pagos que comparten EXPEDIENTE_PAGO en proporción a su monto; si hay un solo pago en el expediente recibe el total. Los legítimos no participan (R4). El estado se deriva igual que en la aplicación: sin expediente → NO INICIADO; SIGAF > 0 → DEVENGADO; si no → EN TRAMITE. El último pase SADE sale de PASES_SADE ordenando por fecha descendente.

7.3 Instalación y uso

Instalación
-- 1. Abrir Database/vw_PowerBI_Redeterminaciones.sql en SSMS conectado a SQL2019-IVC -- 2. El script empieza con USE IVC; y usa CREATE OR ALTER VIEW: se puede re-ejecutar las veces que haga falta -- 3. Requiere SQL Server 2016 SP1 o superior (el servidor es 2019) -- 4. Los índices sugeridos al inicio del script son opcionales; ejecutarlos solo si el refresco resulta lento
📌 Los joins por número de expediente contra PASES_SADE y GEDO usan COLLATE DATABASE_DEFAULT porque esas tablas tienen una collation distinta al resto de la base. No quitar esos COLLATE.
Power BI

Conectar las tres vistas en modo Import y relacionarlas con las tablas ya existentes del modelo por AutorizanteId u ObraId. vw_PBI_Pagos puede reemplazar a la tabla de certificados del modelo, porque ya trae las reliquidaciones como filas con TipoPagoId = 3 y Origen = 'RELIQUIDACION'. Lo único que conviene resolver en DAX son los semáforos por días en buzón, con TODAY() sobre FechaSade.

Verificación
-- Un autorizante paso a paso SELECT * FROM dbo.vw_PBI_Redeterminaciones WHERE CodigoAutorizante = 'XXX' ORDER BY Nro; SELECT * FROM dbo.vw_PBI_Reliquidaciones WHERE CodigoAutorizante = 'XXX' ORDER BY NroRedet, MesAprobacion; -- Control: total reliquidado vs. MontoRedet (deben coincidir cuando los certificados cubren el faltante) SELECT rd.CodigoRedet, rd.MontoRedet, SUM(rq.MontoReliquidacion) AS TotalReliquidado FROM dbo.vw_PBI_Redeterminaciones rd LEFT JOIN dbo.vw_PBI_Reliquidaciones rq ON rq.RedeterminacionId = rd.RedeterminacionId GROUP BY rd.CodigoRedet, rd.MontoRedet;
📌 Validado el 23/09/2026 contra IVC_TEST: las tres vistas se construyen sin errores, la base completa (unos 5.000 pagos) se resuelve en ~110 ms y los montos coinciden con los que calcula la aplicación.

8. Dónde vive el cálculo en la aplicación

PiezaUbicaciónQué hace
Pasos A, B y C Negocio/CalculoRedeterminacionNegocioEF.cs → CalcularMontoRedeterminaciones Agrupa los certificados por autorizante una sola vez (R5), aplica R1 y R2 con los helpers EsMesAnteriorOIgual / EsMesPosterior, calcula MontoRedet y deja el porcentaje ejecutado pre-Salto en RedeterminacionEF.PorcentajeEjecutadoPreSalto para el Paso 3b.
Pasos 1, 2, 3a y 3b Negocio/CalculoRedeterminacionNegocioEF.cs → ListarCertificadosYReliquidaciones Genera las reliquidaciones virtuales (tipo de pago 3) para la pantalla de Certificados. El campo Porcentaje de la reliquidación es el porcentaje aplicado (propio + acumulado pre-Salto si es la primera).
Propiedades calculadas Dominio/RedeterminacionEF.cs MontoRedet y PorcentajeEjecutadoPreSalto son [NotMapped]: existen solo en memoria. Codigo_Redet (sufijo -R1, -R2…) es una columna calculada de la base.
Pantallas AutorizantesEF.aspx · CertificadosEF.aspx Usan ListarAutorizantesYRedeterminaciones y ListarCertificadosYReliquidaciones. Las redeterminaciones aparecen en la grilla de autorizantes como filas con concepto REDETERMINACION y MontoAutorizado = MontoRedet.
Código heredado Negocio/CalculoRedeterminacionNegocio.cs (ADO) Versiones anteriores de la fórmula. Ninguna pantalla las usa para redeterminaciones; no se actualizaron a las reglas vigentes. No tomarlas como referencia.
Métodos con falla conocida ListarAutorizantesCompleto · ListarAutorizantesPaginados Hacen Include(r => r.Autorizante) sobre una propiedad no mapeada; Entity Framework lanza una excepción, el catch la absorbe y devuelven lista vacía. Solo el primero se usa, como respaldo del subtotal del paginador.
